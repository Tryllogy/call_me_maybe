## Description

`call_me_maybe` is a function-calling interpreter built around a local Hugging Face causal language model. The goal of the project is to read a list of available function definitions and a list of natural-language prompts, then produce a JSON output that maps each prompt to the most relevant function name and its parameters.

The project is designed to solve a constrained function selection task: instead of generating free-form text, the model must output a single JSON object shaped like `{"name": ..., "parameters": ...}`. The repository includes sample function definitions, sample prompts, and an output file generated by the interpreter.

## Instructions

### Requirements

- Python 3.10 or newer
- Internet access on first run, so the Hugging Face model can be downloaded
- Enough RAM to load the local model defined in `llm_sdk/`

### Installation

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

If you prefer the provided Makefile workflow:

```bash
make install
source <venv>/bin/activate
make
```

### Execution

The main entry point expects three arguments:

- `--functions_definition`: path to the JSON file describing available functions
- `--input`: path to the JSON file containing prompts
- `--output`: path to the JSON file that will receive the generated function calls

- You can replace function definitions / input / output with the following flags:
 	- FUNCTIONS_DEFINITION=<your_functions.json>
	- FUNCTION_CALLING_TESTS=<your_prompts.json>
	- OUTPUT=<your_output_file.json>

Example using the bundled dataset:

```bash
uv run python -m src [–functions_definition <function_definition_file>]
[–input <input_file>] [–output <output_file>]
```

```bash
uv run python -m src --functions_definition data/input/functions_definition.json --input data/input/function_calling_tests.json --output data/output/function_calls.json
```

The Makefile contains a shortcut for the same workflow:

```bash
make run
```

The first run may take longer because the model weights and tokenizer files are downloaded from the Hugging Face Hub.

## Example Usage

Input prompt example:

```json
{
	"prompt": "Greet john"
}
```

Expected output shape:

```json
{
	"prompt": "Greet john",
	"name": "fn_greet",
	"parameters": {
		"name": "john"
	}
}
```

With the provided sample files, the interpreter reads all prompts from `data/input/function_calling_tests.json` and writes the result to `data/output/function_calls.json`.

## Algorithm Explanation

The decoding strategy is a lightweight constrained-decoding approach implemented in `src/llm.py`.

1. The interpreter first builds a compact instruction block with the allowed functions and their parameter schemas.
2. For each prompt, it prefixes the generation with `{"name":"` so the model starts directly inside the JSON object.
3. It then performs greedy token-by-token decoding: at each step, the model logits are computed for the current token sequence, and the highest-logit token is selected.
4. Decoding continues until the brace counter returns to zero. The code tracks how many `{` and `}` tokens have been emitted and stops when the generated JSON object is closed.
5. The final token sequence is decoded into text, parsed as JSON, and converted into the output structure expected by the project.

This is not a hard grammar mask or a full finite-state decoder. The constraint comes from a combination of prompt shaping, a forced JSON prefix, greedy selection, and brace balancing. In practice, this keeps the generation focused on a single JSON object while remaining simple and fast to implement.

## Design Decisions

The implementation intentionally stays small and explicit.

- A local model is used through `Small_LLM_Model` in `llm_sdk/__init__.py`, which keeps the project self-contained and avoids external API dependencies.
- Input validation is handled with `ParsingValidator` in `src/parsing_validator.py` so malformed function definitions, inputs, or output paths fail early.
- Output is always written as a JSON array, which makes downstream evaluation and inspection easier.
- The decoding loop is greedy instead of sampling-based. This favors determinism and reproducibility over creative generation.
- The prompt format is strict and minimal so the model sees only the information needed to choose a function and emit parameters.

## Performance Analysis

Accuracy, speed, and reliability depend mostly on the local model and the quality of the function schemas.

- Accuracy is good when the prompt clearly matches one of the provided function descriptions. It is weaker for ambiguous prompts because the implementation does not use a hard grammar or a verifier that checks semantic correctness of the chosen parameters.
- Speed is limited by token-by-token generation. Each new token requires another forward pass through the model, so the approach is slower than a single-pass classifier or a batched decoder.
- Reliability is improved by deterministic greedy decoding and schema validation, but the system can still produce invalid JSON if the model diverges from the expected format.
- Memory usage is controlled by selecting a relatively small causal model and by using inference-only mode.

## Challenges Faced

The main difficulties were format control and robustness.

- Getting the model to emit only JSON was non-trivial, so the prompt was tightened and generation starts from a JSON prefix.
- Closing the generation at the right time required explicit brace tracking because the model can otherwise keep generating extra text.
- Validating heterogeneous function definitions required clear checks for required keys such as `name`, `description`, `parameters`, and `returns`.
- Model loading and tokenizer compatibility are handled inside the SDK wrapper so the interpreter code remains focused on task logic.

## Testing Strategy

Validation is done at two levels.

- Structural validation: `ParsingValidator` checks the shape of the function definitions, input data, and output path before inference starts.
- Functional validation: the bundled dataset in `data/input/function_calling_tests.json` can be processed end-to-end and the result inspected in `data/output/function_calls.json`.
- Manual checks: the generated JSON is reviewed to confirm that each entry contains a prompt, a function name, and a parameters object.
